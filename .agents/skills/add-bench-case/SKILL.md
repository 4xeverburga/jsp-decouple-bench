# Add a bench case — one behavior, one slice

A **slice** is a feature boundary (`vote-flow`); a **case** is one
observable behavior of it. One case = one directory, named
`<slice>__<behavior>`, under the sample:

```
samples/<sample>/cases/<slice>__<behavior>/
├── case.json      # hand-written contract: e2e notes + the db table specs
├── flow.py        # the Playwright flow — single source of truth (hand-written)
├── expect.json    # frozen golden — GENERATED by `main.py capture`
└── images/        # optional step shots kept from an investigation
```

The bench owns all four. `expect.json` is the answer key: it never leaves
this repository and nothing in the sample tree hints at it.

## Acceptance rule — a slice must fully cover one controller

A slice is **not done** until its cases, taken together, **completely
cover at least one controller**: the controller whose routes the slice
asks an agent to decouple. "Completely" means:

- every handler method (route + HTTP verb) of that controller class is
  executed by at least one case;
- every reachable branch in those handlers has a case: success,
  validation failure, permission/karma denial, not-found;
- every handler not driven is listed in `not_driven`, and every branch
  not driven is *omitted* with its reason. A branch is omitted only when
  the app cannot reach it from a state it produces itself — through its
  own UI, from the dump plus legitimate seed rows: a defensive null check
  on an orphaned row, a `catch` for an infrastructure failure, an
  external OAuth/Solr/mail service, or a server refusal the page's own
  script already prevents (mamute's `links-behaviour.js` refuses a vote
  on one's own question before any request leaves). "Hard to drive" is
  not a reason — add the case, seeded if it needs rows the dump lacks.
  "The golden would be a crash on impossible data" is a reason: a case
  that records a 500 grades bug-for-bug fidelity, not behaviour.

These targets grade the cases, never an agent: they read the pin's code,
out of band, while a solve is judged only on side effects. Handlers 100%,
slice branches 100% covered or omitted, lines no target of their own.
Mutation testing, once it exists, is the cases' actual power (≥ 80% of
non-equivalent mutants killed); coverage only says where cases are
missing.

One behaviour case on a controller with five handlers does not make a
slice. If the controller cannot be driven to this level through the UI,
pick another controller or do not make it a slice. The claim is recorded
in the manifest (§8) and re-checked by `dataset-ready-check`.

## Procedure

### 1. Design the behavior (read the sample's source)

Trace the controller/route for the behavior in the sample checkout
(`../<sample>/src`). Note the exact route paths, the widget that triggers
it, permission/karma gates (and whether the seeded actor bypasses them),
and which tables the DAO layer touches. Split multi-behavior ideas into
separate cases — granularity makes verdicts diagnosable.

**Inventory the controller first.** List every handler of the target
controller (method, route, verb, guard conditions, error branches) and
plan which case drives each one. Gaps in this list are the cases you
still have to write; it becomes the `handlers` map in §8.

**Then read what the page does before the request.** Legacy pages guard
their own controls: a tag that withholds a form (mamute's
`canAnswer.tag`), a script that swaps a click for a popup
(`links-behaviour.js`). A server refusal behind such a guard is reached
only through a stale page (§3), or not at all — and then it is omitted,
not written. The page-side refusal is itself a behaviour worth a case
when the slice renders the data it decides on.

### 2. Author `case.json`

Copy a sibling case of the same sample and adjust. The shape is the
`functional_parity` case contract:

```json
{
  "sample": "mamute",
  "case": "vote-flow__upvote-increments-count",
  "e2e": {
    "routes": ["/login", "/question/{id}/voto/positivo"],
    "locale": "en-US", "timezone_id": "UTC",
    "viewport": {"width": 1280, "height": 800},
    "auth": "mixed",
    "credentials": "env:MAMUTE_ADMIN_USER,MAMUTE_ADMIN_PASSWORD",
    "requires_db_reset": true,
    "artifacts": ["vote_count_before", "vote_count_after"]
  },
  "db": {"tables": [{"name": "Vote", "key_columns": ["id"],
                     "ignore_columns": ["createdAt"]}], "notes": ""}
}
```

`db.tables` is **read by the capture**, not decoration: it is where the
author declares which tables the behaviour owns and which columns are
volatile. `locale`, `timezone_id` and `viewport` are the determinism
contract — never omit them, never take them from the host; the effective
values come from `settings.py` (`BENCH_*` in `bench.env`), and the case states
the same ones so a reviewer can see them.

### 3. Author `flow.py`

Rules (all hard-won — violating any of these cost a debug cycle):

- **Self-contained arrange**: sign up / create entities in-flow with
  deterministic fixed credentials; act with the seeded actor, whose
  credentials come from `os.environ` only (`capture` and `score` inject
  the sample's `env/.env`). Why a literal must never appear is
  `bench-case-principles` §"Self-containment".
- **Wait for submit navigations explicitly**:
  `with page.expect_navigation(wait_until="load"): page.click(...)` —
  `click` + `wait_for_load_state` races the redirect.
- **Wait for signals, never sleep**: `page.expect_response("**/route")`
  around the action click; `wait_for_load_state("networkidle")` after
  navigation; `wait_for_function` for DOM updates — and when building a
  JS predicate with `%` formatting, check the braces survive it (a
  missing `}` here once broke every vote wait). An AJAX widget that
  updates the count optimistically (mamute's `fakeUpdateIncrement`) has
  not finished when the count changes: wait for its own busy marker to
  clear (`.vote-option.stop`) before the next click.
- **The one allowed timed wait** is a window the app itself enforces and
  no signal ends. mamute refuses a user's second post within 15 s
  (`InputManager.SPAM_TIME`) with a 403 whose message counts the seconds
  left — before any validator runs. A flow that posts twice as one user
  waits it out with `page.wait_for_timeout(FLOOD_WAIT_MS)`, a named
  constant whose comment cites the source. The refusal itself is omitted:
  its message is time-dependent.
- **Reload between two acts on the same state**: vote, reload, unvote.
  The second act then starts from what the server stored, not from the
  widget's own memory, so an agent that never persists the first act
  fails the case.
- **A server refusal the page prevents is reached through a stale
  page**: open the question in two tabs (`page.context.new_page()`),
  act in the first, submit from the second, which still shows the form.
  That is a real user's path to the validator's error redirect; a fresh
  page withholds the form.
- **One submit is one behaviour**: a submission with several invalid
  fields is one case, and the exact DOM comparison catches any one
  message going missing. Two submissions are two cases.
- **Timed waits are data, not literals**: `CASE_TIMEOUT_MS` comes from
  `settings` (`bench.env` → `BENCH_CASE_TIMEOUT_MS`). No `timeout=5000` in a
  flow.
- **Legacy widgets need UI driving**: select2 v3 inputs are hidden —
  click `.select2-container`, `fill(".select2-input", ...)`,
  `wait_for_selector(".select2-result-selectable")`, click the result.
  Filling the hidden input times out.
- **Snapshots**: normalize `page.content()` (strip `<script>/<style>`,
  collapse whitespace) before/after the act; return the artifacts dict
  whose keys are exactly `e2e.artifacts`.
- **A wait for a graded outcome must fail loudly**: `cases.drive` turns an
  `AssertionError` — or a Playwright timeout — into `FlowAssertionError`,
  and the scorer records that as `INCORRECT` with the page it ended on and
  the DB delta it caused. So make the timeout message carry the diagnosis
  (count, rendered text, URL); do not swallow it into a bare `assert`.

### 4. Author the db contract

Start from a sibling case's table list for the same slice, then let the
capture correct it empirically: it snapshots exactly the tables you
declared, and a table you forgot simply does not appear in the delta.
Key columns come from `DESCRIBE <table>` (`\d` in psql) — join tables in
mamute use `tags_id`/`watchers_id`, not `Tag_id`/`Watcher_id`. What counts
as volatile, and what to exclude on purpose, is `bench-case-principles`
§"The delta pattern".

The client runs **inside the `db` service** of the case's stack, and the
dialect is the manifest's (`bindings.db.options.dialect`, `mysql` or
`postgres`). Nothing is installed on the host and no port is published.

### 5. Capture the golden

The stack is the bench's (`samples/<sample>/env/`), so the sample
must have one before a case can be captured. `BENCH_CHECKOUT` names the
sample's **repository** (the pin is cut from it); each case's stack
picks a free host port itself and plays against the sample's `target_url`
in `seeds/samples.json` on that port — never export a port or a URL by
hand:

```bash
cd jsp-decouple-bench
BENCH_CHECKOUT=$PWD/../mamute \
  uv run python main.py capture --manifest 3 \
    --case vote-flow__upvote-increments-count
```

What it does, in order: archive the pinned commit into
temporary checkout (refusing a pin that carries a stack
file), build and start **one stack per case** from `env/compose.yaml`,
snapshot the declared tables, run `flow.py` once, snapshot again, and
write `expect.json` = `{sample, case, sample_commit, captured_at, db:
{<before/after delta>}, artifacts: {...}}`. The staged failure screenshot
is dropped: a capture is a run that passed by definition.

**Never hand-edit `expect.json`.** If a case fails on an untouched tree,
the environment or a normalizer rule is wrong — re-capture from the
pristine pin, and understand *why* it differed first
(`bench-case-principles` §"The golden is generated").

### 6. Determinism gate (mandatory)

Run the capture a second time and diff. `captured_at` is provenance and
is the only field allowed to move:

```bash
uv run python main.py capture --manifest 3 --case <case>   # again
git diff -U0 -- samples/<sample>/cases/<case>/expect.json \
  | grep '^[+-]' | grep -v captured_at   # must print nothing
```

If anything else differs, the environment — or a normalization rule — is
not deterministic; stop and fix that first, never "accept" the second
golden.

Equivalent, and cheaper for a batch: score the manifest against a no-op
record of the sample (an empty `diff.patch` on the pin, no `manifest_id`
in `record.json`, e.g. `out/solves/noop-<sample>-<sha8>/`). Parity
replays every case on a fresh stack against its golden, normalized
exactly as a solve would be; `all_must_pass 1.000` is the second run.
`trace_similarity` fails a no-op outright and asks no judge. Two captures inside the same minute prove less than they look
like: a volatile value with a minute's resolution hides in both (an
openclinica golden once kept the build *time* for exactly that reason).

### 7. Prove the controller is fully covered (mandatory)

Coverage is an argument backed by evidence. The argument is the handler
map in `scope.covers` (§8); the evidence is `main.py coverage`
(`src/controls/`), which replays each case on its own stack with a
JaCoCo agent attached and reports, per case and for all of them, slice
and controller lines and branches:

```bash
BENCH_CHECKOUT=$PWD/../mamute uv run python main.py coverage --manifest 3
```

It writes under `out/coverage/<manifest>/`, which git ignores. Copy
`report.md` to `samples/<sample>/coverage/<manifest>.md` and commit it
with the cases it measured, so every change to a manifest's cases carries
the numbers it moved. Read the slice branches against §"Acceptance rule":
each one missing is a case to write or a branch to omit, with its reason
in the manifest's ROADMAP entry until `scope.covers` can hold it.

### 8. Wire it into a manifest

Edit `seeds/manifests.json` directly — seeds are the source of truth
there is no database to sync:
the row carries no prompt; the ask goes in
`seeds/prompts/manifests/<name>.md`, named after the row's `name`, and
the loader refuses a manifest whose file is missing.

```json
{
  "id": 3,
  "sample": "mamute",
  "name": "vote-flow",
  "task_type": "decouple_slice",
  "solve_time_limit_minutes": 60,
  "score_time_limit_minutes": 60,
  "scope": {
    "cases": ["vote-flow__upvote-increments-count",
              "vote-flow__downvote-increments-count"],
    "routes": ["..."]
  }
}
```

Then confirm the case count moved:

```bash
uv run python main.py manifests
```

Record the coverage claim in the same entry's `scope.covers` (data only;
it is the answer key's index and never reaches the agent). `slice` is
what the manifest's prompt moves behind the backend, read from the
prompt and not from the cases; each slice handler names the case meant
to drive it:

```json
"covers": {
  "controllers": {
    "org.mamute.controllers.VoteController": {
      "slice": ["voteUp", "voteDown", "voteUpRemoval", "voteDownRemoval"],
      "handlers": {"voteUp": "vote-flow__upvote-increments-count"},
      "not_driven": {"<handler>": "<why it cannot be reached here>"}
    }
  }
}
```

Every case also needs its `scope.trace` entry — the requests whose work
must move, as `trace_similarity` sees them. Copy the labels from the
case's captured `trace.json` (`"SERVER POST /Question/{n}/voto/positivo
-> 200"`), never from memory: a label that matches no request is a
judge asked about nothing.

**Adding cases to a manifest that has been scored** bumps its `version`,
so earlier scores are not compared with later ones. An existing case and
its golden are never edited. One may be deleted (git keeps it) once newer
cases check everything it checks, final rows included: a removal case
that undoes its vote does not replace the case whose delta shows the
vote standing.

### 9. Prove the case can fail (sensitivity)

A green golden proves nothing about the case's power. Break the behaviour
on a scratch copy of the pin (comment out the `save(...)` the flow
exercises) and run `main.py score` against it: the case must come back
`INCORRECT`, listing the tables that differ, with a screenshot under
`out/evidence/<sample>/`. If the case stays green, the artifacts you
assert on do not cover the behaviour — back to §1.
