# Test slice — add one behavior case to a sample

A **slice** is a feature boundary (`vote-flow`); a **case** is one
observable behavior of it. One case = one directory, named
`<slice>__<behavior>`, under the sample:

```
src/samples/<sample>/cases/<slice>__<behavior>/
├── case.json      # hand-written contract: e2e notes + the db table specs
├── flow.py        # the Playwright flow — single source of truth (hand-written)
├── expect.json    # frozen golden — GENERATED by `main.py capture`
└── images/        # optional step shots kept from an investigation
```

The bench owns all four. `expect.json` is the answer key: it never leaves
this repository and nothing in the sample tree hints at it.

## Acceptance rule — a slice must fully cover one controller

A slice is **not done** until its cases, taken together, **completely
cover at least one controller**: the controller whose routes the slice
asks an agent to decouple. "Completely" means:

- every handler method (route + HTTP verb) of that controller class is
  executed by at least one case;
- every reachable branch in those handlers has a case: success,
  validation failure, permission/karma denial, not-found;
- every handler or branch not driven is listed individually, with the
  reason it cannot be reached in the deterministic environment (needs an
  external OAuth/Solr/mail service, dead defensive code). "Hard to drive"
  is not a reason — add the case.

One behaviour case on a controller with five handlers does not make a
slice. If the controller cannot be driven to this level through the UI,
pick another controller or do not make it a slice. The claim is recorded
in the manifest (§8) and re-checked by `dataset-ready-check`.

## Procedure

### 1. Design the behavior (read the sample's source)

Trace the controller/route for the behavior in the sample checkout
(`../<sample>/src`). Note the exact route paths, the widget that triggers
it, permission/karma gates (and whether the seeded actor bypasses them),
and which tables the DAO layer touches. Split multi-behavior ideas into
separate cases — granularity makes verdicts diagnosable.

**Inventory the controller first.** List every handler of the target
controller (method, route, verb, guard conditions, error branches) and
plan which case drives each one. Gaps in this list are the cases you
still have to write; it becomes the `handlers` map in §8.

### 2. Author `case.json`

Copy a sibling case of the same sample and adjust. The shape is the
`functional_parity` case contract:

```json
{
  "sample": "mamute",
  "case": "vote-flow__upvote-increments-count",
  "e2e": {
    "routes": ["/login", "/question/{id}/voto/positivo"],
    "locale": "en-US", "timezone_id": "UTC",
    "viewport": {"width": 1280, "height": 800},
    "auth": "mixed",
    "credentials": "env:MAMUTE_ADMIN_USER,MAMUTE_ADMIN_PASSWORD",
    "requires_db_reset": true,
    "artifacts": ["vote_count_before", "vote_count_after"]
  },
  "db": {"tables": [{"name": "Vote", "key_columns": ["id"],
                     "ignore_columns": ["createdAt"]}], "notes": ""}
}
```

`db.tables` is **read by the capture**, not decoration: it is where the
author declares which tables the behaviour owns and which columns are
volatile. `locale`, `timezone_id` and `viewport` are the determinism
contract — never omit them, never take them from the host; the effective
values come from `settings.py` (`BENCH_*` in `.env`), and the case states
the same ones so a reviewer can see them.

### 3. Author `flow.py`

Rules (all hard-won — violating any of these cost a debug cycle):

- **Self-contained arrange**: sign up / create entities in-flow with
  deterministic fixed credentials; act with the seeded actor whose
  credentials come from `os.environ` only. `main.py capture` and
  `main.py score` both inject the sample's `src/samples/<sample>/env/.env`
  into the process environment, so the flow reads
  `os.environ["MAMUTE_ADMIN_PASSWORD"]` — never a literal password, never
  a value from the tree.
- **Wait for submit navigations explicitly**:
  `with page.expect_navigation(wait_until="load"): page.click(...)` —
  `click` + `wait_for_load_state` races the redirect.
- **Wait for signals, never sleep**: `page.expect_response("**/route")`
  around the action click; `wait_for_load_state("networkidle")` after
  navigation; `wait_for_function` for DOM updates — and when building a
  JS predicate with `%` formatting, check the braces survive it (a
  missing `}` here once broke every vote wait).
- **Timed waits are data, not literals**: `CASE_TIMEOUT_MS` comes from
  `settings` (`.env` → `BENCH_CASE_TIMEOUT_MS`). No `timeout=5000` in a
  flow.
- **Legacy widgets need UI driving**: select2 v3 inputs are hidden —
  click `.select2-container`, `fill(".select2-input", ...)`,
  `wait_for_selector(".select2-result-selectable")`, click the result.
  Filling the hidden input times out.
- **Snapshots**: normalize `page.content()` (strip `<script>/<style>`,
  collapse whitespace) before/after the act; return the artifacts dict
  whose keys are exactly `e2e.artifacts`.
- **A wait for a graded outcome must fail loudly**: `cases.drive` turns an
  `AssertionError` — or a Playwright timeout — into `FlowAssertionError`,
  and the scorer records that as `INCORRECT` with the page it ended on and
  the DB delta it caused. So make the timeout message carry the diagnosis
  (count, rendered text, URL); do not swallow it into a bare `assert`.

### 4. Author the db contract

Start from a sibling case's table list for the same slice, then let the
capture correct it empirically: it snapshots exactly the tables you
declared, and a table you forgot simply does not appear in the delta.
Key columns come from `DESCRIBE <table>` (`\d` in psql) — join tables in
mamute use `tags_id`/`watchers_id`, not `Tag_id`/`Watcher_id`. Ignore
every volatile column (all timestamps, counters not asserted on).
Exclude auth plumbing (e.g. `UserSession`) deliberately and say why in
`notes`.

The client runs **inside the `db` service** of the case's stack, and the
dialect is the manifest's (`bindings.db.options.dialect`, `mysql` or
`postgres`). Nothing is installed on the host and no port is published.

### 5. Capture the golden

The stack is the bench's (`src/samples/<sample>/env/`), so the sample
must have one before a case can be captured. `BENCH_CHECKOUT` names the
sample's **repository** (the pin is cut from it) and `BENCH_BASE_URL` the
address its stack will publish:

```bash
cd jsp-decouple-bench
BENCH_CHECKOUT=$PWD/../mamute \
BENCH_BASE_URL=http://localhost:8090 \
APP_HTTP_PORT=8090 \
  uv run python main.py capture --manifest 3 \
    --case vote-flow__upvote-increments-count
```

What it does, in order: archive the pinned commit into
`out/workspaces/capture-<id>/` (refusing a pin that carries a stack
file), build and start **one stack per case** from `env/compose.yaml`,
snapshot the declared tables, run `flow.py` once, snapshot again, and
write `expect.json` = `{sample, case, sample_commit, captured_at, db:
{<before/after delta>}, artifacts: {...}}`. The staged failure screenshot
is dropped: a capture is a run that passed by definition.

**Never hand-edit `expect.json`.** If a case fails on an untouched tree,
re-capture from the pristine pin *and understand why it differed* before
accepting the new golden.

### 6. Determinism gate (mandatory)

Run the capture a second time and diff. `captured_at` is provenance and
is the only field allowed to move:

```bash
git stash list >/dev/null   # (state check, nothing to do)
uv run python main.py capture --manifest 3 --case <case>   # again
git diff -U0 -- src/samples/<sample>/cases/<case>/expect.json \
  | grep '^[+-]' | grep -v captured_at   # must print nothing
```

Ids are stable because every fresh boot replays the same seed. If anything
else differs, the environment is not deterministic; stop and fix that
first — do not "accept" the second golden.

### 7. Prove the controller is fully covered (mandatory)

Coverage is an argument backed by evidence, not a claim: for the target
controller, list every handler and point at the case that drives it. That
map is `scope.covers.handlers` in the manifest (§8).

A dynamic measurement is optional and **out of band**: attach a JaCoCo
agent to the app's JVM on a throwaway clone, dump one `.exec` per case
(each case runs on its own pristine stack — never `output=file`, the next
boot truncates it), and read the controller's row with `jacococli
report`. The instrumentation is never committed to the sample's pin and
never becomes part of the stack. The old harness had a
`scripts/measure-coverage.sh` for this; it was not carried over
(`ROADMAP.md`). Until it is, the handler map is the reviewable artifact
and a JaCoCo run is extra confirmation, not a gate.

### 8. Wire it into a manifest

Edit `seeds/manifests.json` directly — seeds are the source of truth
there is no database to sync:

```json
{
  "id": 3,
  "source": "mamute",
  "name": "vote-flow",
  "task_type": "decouple_slice",
  "scope": {
    "cases": ["vote-flow__upvote-increments-count",
              "vote-flow__downvote-increments-count"],
    "routes": ["..."]
  }
}
```

Then confirm the case count moved:

```bash
uv run python main.py manifests
```

Record the coverage claim in the same entry's `scope.covers` (data only;
it is the answer key's index and never reaches the agent):

```json
"scope": {
  "cases": ["..."],
  "routes": ["..."],
  "covers": {
    "controller": "br.com.caelum.vraptor.controller.VoteController",
    "handlers": {
      "tryToVoteVotable": "vote-flow__upvote-increments-count",
      "tryToRemoveVoteVotable": "vote-flow__downvote-increments-count"
    },
    "not_driven": {"<handler>": "<why it cannot be reached here>"}
  }
}
```

### 9. Prove the case can fail (sensitivity)

A green golden proves nothing about the case's power. Break the behaviour
on a scratch copy of the pin (comment out the `save(...)` the flow
exercises) and run `main.py score` against it: the case must come back
`INCORRECT`, listing the tables that differ, with a screenshot under
`out/evidence/<sample>/`. If the case stays green, the artifacts you
assert on do not cover the behaviour — back to §1.
